# MooBee Fetch v0.2.1 — peer discovery safety and validation

## Evidence collected on Stream VPS (12 October 2026)

- UDP DNS works from VPS host and MooBee Fetch Docker bridge.
- DHT UDP probes received valid answers from `dht.transmissionbt.com:6881`
  and `dht.libtorrent.org:25401`; `router.bittorrent.com:6881` did not reply.
- aria2 binds IPv4 DHT UDP 6881 and peer TCP 6881. Reachability to DHT
  routers alone does not prove peer discovery works.
- The official Ubuntu 24.04.5 LTS torrent tracker returned a seeder count of
  440 but only **one** peer address in the particular announce response.
- A direct TCP connection to that one peer succeeded and the BitTorrent
  handshake was valid. The peer did **not** advertise the extended messaging
  flag used for BEP-10/`ut_metadata`. Magnet metadata remained unavailable.
- This does **not** prove all torrent peers reject metadata. A complete
  `.torrent` file supplies the metadata itself.

## Feature gates / threat model

The uploader strips **all user-provided tracker and web-seed URLs**. With
`FETCH_CURATED_TRACKERS_ENABLED` absent/0, both magnet and `.torrent` uploads
use DHT-only discovery, as before. No changes to live service behavior are
intended.

Opt-in profiles if and only if *separate network egress protections* are
reviewed, deployed and tested by the VPS operator:

- `dht` (default): aria2 receives no tracker URLs from the transfer.
- `ubuntu`: a literal `http://torrent.ubuntu.com:6969/announce` tracker,
  only if the uploaded magnet or sanitized torrent matches one of two exact
  official Ubuntu control hashes from our verified tests:
  `a3b4136a174e30b121a6bb6ab75b577ea7eda5f3` (24.04.5 LTS) and
  `e4f19cf636409b72571766c2ae89c98fc21a109d` (26.04.1).
- `public`: two hardcoded community-operated public tracker URLs
  `udp://tracker.opentrackr.org:1337/announce` and
  `udp://open.stealth.si:80/announce`; functionality, policies and uptime
  are not guaranteed. They are **not** automatically extracted from inputs.

**WARNING:** static tracker destinations do **not** secure the downloader.
Trackers, DHT, peer exchange, DNS, and inbound/outbound peer connections may
still expose the downloader to arbitrary public/private addresses. Docker's
bridge network and `cap_drop: ALL` are **not** outbound firewall controls.
A peer or tracker could direct the client to a private RFC1918, link-local,
loopback, metadata or Tailnet address. Using a tracker by hostname can also
allow DNS-related changes. Before enabling curated trackers, enforce
*downloader-specific* outbound restrictions for IPv4 and IPv6 at the VPS/
network level; deny local LAN/VPC, Tailscale 100.64.0.0/10, loopback, link-local
169.254.0.0/16 and cloud metadata networks, and test without disturbing other
MooBee services. No egress firewall is implemented by this release.
Never deploy guessed host firewall rules to a remotely administered VPS.

The application uses a config flag (`FETCH_CURATED_TRACKERS_ENABLED=1`) as
an **operator opt-in only**. Setting that flag is **not** an egress safety test
or proof of isolation. Leave it off until a separately vetted firewall is
implemented. No custom tracker URLs, user-supplied hosts or web seeds.

## Code and verification

The API adds `GET /api/discovery/profiles`; it reports only profile names and
whether curated modes have been enabled, not secrets, peer IPs or tracker URLs.

- Magnet `POST /api/transfers` may now include
  `{"tracker_profile":"dht"|"ubuntu"|"public"}`; default `dht`.
- `.torrent` upload uses `X-MooBee-Discovery-Profile: dht|ubuntu|public`.
- Both paths produce identical server-defined aria2 `bt-tracker` options;
  raw `tr`, `ws`, `announce` or `announce-list` inputs are always stripped.
- Metadata state labels now distinguish connected peers that have not
  completed metadata exchange, instead of implying progress.

CI runs Python tests, import validation, and Docker builds. This does not
establish connectivity to any live tracker or compliant firewall.

### Important operational detail

The GitHub Compose `--dht-entry-point=dht.transmissionbt.com:6881` reflects
the manual setting already tested on the Stream VPS, so a source sync should
retain it. Existing downloads and `.aria2-session` are not deleted; a short
MooBee Fetch downloader restart interrupts active transfers. For rollback,
restore the saved Compose file and previous Git source revision, rebuild only
the two MooBee Fetch services; keep the separate `.env` and download data.

## Control trial when isolation is approved

Use only an official Ubuntu `.torrent` through the UI with profile `ubuntu`.
A `.torrent` supplies its info dictionary and bypasses peer `ut_metadata`
requirements, but the ISO content may download: ensure adequate free space,
permission to download, bandwidth limits, and actual peer reachability.
No software test can promise the download speed or completion.
